# SD DMA write repair and board verification — 2026-10-09

The first-sector logging failure is fixed and verified on the connected
STM32F407VG / dual-BMI270 board, USB serial `3154365B3034`. Work started from
GitHub revision `b7936e2`. These are USB-powered, disarmed bench results.

## Cause and change

The previous image mounted FAT32 and allocated a log, but immediately stopped
with `SDIO_STA=1052736`, `DMA2_HISR=65536` and zero committed bytes. The SDIO
snapshot has no data error; DMA reports only stream 6's FIFO flag, `FEIF6`.
Our adapter incorrectly classified that flag alone as a fatal transfer error.

ST's [SD_DMAError implementation](https://github.com/STMicroelectronics/stm32f4xx-hal-driver/blob/master/Src/stm32f4xx_hal_sd.c)
ignores an isolated DMA FIFO error. The revised adapter follows that policy,
while continuing to reject DMA transfer/direct-mode errors and SDIO CRC,
timeout, underrun and start-bit errors. Success still requires SDIO DATAEND,
DMA transfer complete, a disabled DMA stream, and subsequent CMD13 reporting
READY_FOR_DATA in TRANSFER state. The existing one-second operation deadline
remains in force. A FIFO warning alone neither fails nor completes a sector.

`SD_DBG` adds `fifo_warn`, the number of transfers on which FEIF6 was observed
at least once. It is a diagnostic counter, not a dropped/corrupt-record count.
The warning occurs on this board's successful writes, so a rising count with
`active=1`, increasing `bytes`, and zero drops is expected. All existing raw
failure registers remain available. No runtime filesystem calls or blocking
waits were added.

To read the card independently of the running logger, a temporary read-only
utility mounted the existing file with `FA_READ`. It did not create, format,
truncate or delete card files. The verified flight image was restored after
the read. This utility is kept in ignored build output and is not part of the
flight firmware. Normal flight startup creates the next unused log as before.

The decoder stopped at the preallocated tail after the valid prefix; 40 bytes
of an unfinished record remained at the end of that prefix. Reset into DFU
does not promise to drain the RAM ring or finish the current sector. The test
does not claim zero loss at shutdown or durability through sudden power loss.

The final board reported `flight_enabled=1`, `armed=0`, `timing_fault=0`, both
IMUs healthy, and BMP581 healthy. Receiver power stayed off; no actuator or
flight test was performed. The magnetometer's separately observed startup
problem was outside this repair.
